## <a name=''></a>1. 引言

### <a name='-1'></a>1.1. 编写目的

本测试报告用于验证证券账户与资金账户管理子系统的功能正确性、业务规则正确性、接口可用性、安全性及稳定性。通过对系统各模块进行功能测试、边界测试、压力测试、接口测试和安全性测试，评估系统是否满足设计要求，并为后续联调与验收提供依据。

本项目涉及的相关人员与子系统有：账户管理人员，交易系统管理子系统，交易客户端子系统

### <a name='-1'></a>1.2. 项目背景

本项目为证券交易系统中的账户业务子系统，负责证券账户与资金账户的生命周期管理，并为其他交易系统提供账户状态、资金信息、账户信息更新及持仓信息支持。

### <a name='-1'></a>1.3. 术语与缩写解释

| 术语               | 含义     |
| ---------------- | ------ |
| Security Account | 证券账户   |
| Fund Account     | 资金账户   |
| Investor         | 投资者    |
| Staff            | 工作人员   |
| Auth Token       | 认证令牌   |
| Holding          | 持仓     |
| Operation Log    | 操作日志   |
| DAO              | 数据访问层  |
| DTO              | 数据传输对象 |

### <a name='-1'></a>1.4. 系统概述

本项目源于浙江大学 **2026夏学期 软件工程基础** 课程，目的在于构建一个完整的股票交易系统，主要包括六大业务：证券账户业务、资金账户业务、交易客户端、股票中央交易系统、网上信息发布、交易系统管理。

其中我们组负责：证券账户业务、资金账户业务。功能主要有：
| 业务模块   | 功能描述                            |
| ------ | ------------------------------- |
| 证券账户管理 | 支持证券账户的开户、挂失、补办及销户等生命周期管理操作。    |
| 资金账户管理 | 支持资金账户的开户、存取款、密码修改、挂失、补办及销户等操作。 |
| 查询服务   | 支持资金账户余额及证券账户持仓信息查询。            |
| 身份认证   | 支持投资者和工作人员的身份认证与登录。             |
| 交易服务  | 支持交易客户端调用接口调用来返回交易信息  。             |

### <a name='-1'></a>1.5. 测试对象——账户业务子系统说明
本次测试对象为证券账户与资金账户管理子系统前、后端服务。    测试范围包括：
- Controller层
- Service层
- DAO层
- 数据库
- 外部接口
- 内部接口
- 前端页面

### <a name='-1'></a>1.6. 测试内容

| 测试名称 | 目的 | 内容 |
| --- | --- | --- |
| 模块功能测试 | 检测各个模块的功能是否全部实现 | 开户、存款、取款、挂失、补办、销户等基本功能 |
| 边界值测试 | 检测系统能否正常处理边界值 | 非法金额、非法身份证、空或非法参数 |
| 压力测试 | 测试系统的承受能力 | 高并发查询、连续交易回调 |
| 模块接口测试 | 测试与其他模块的接口是否完好，能否最后实现集成测试 | 运行本子系统，观察数据库里的数据变化，检查子系统间的交互。 |

### <a name='-1'></a>1.7. 测试设备

**硬件设备：**
- 服务器：本地开发环境
- 客户端：PC机

**软件设备：**
- 浏览器：Chrome、Edge等现代浏览器
- 测试工具：Postman（接口测试）、JMeter（压力测试）
- 数据库：MySQL
- 开发框架：Spring Boot + Vue.js

### <a name='-1'></a>1.8. 测试进度安排

| 阶段 | 内容 |
| --- | --- |
| 第一阶段 （预备阶段） | 测试人员阅读本子系统的设计文档，熟悉各个功能模块所实现的具体功能，了解本子系统各个输入数据的边界情况。同时，寻找用于测试相关的工具。 |
| 第二阶段（准备阶段） | 测试人员根据各个功能模块的功能，编写测试用例，准备好测试所使用的输入数据。 |
| 第三阶段（测试阶段） | 测试人员针对已经开发出来的子系统，用测试用例对系统进行模块功能测试，找出本子系统中存在的缺陷或错误。 |
| 第四阶段（后期阶段） | 本子系统编码人员根据测试阶段的结果调整程序代码，修复存在的缺陷或错误。 |

### <a name='-1'></a>3.3. 测试结果分析

从测试结果看，账户管理子系统对基础输入边界和业务边界均能进行有效控制。开户信息缺失、存款金额为 `0`、错误安全证书码等非法输入会被前端或后端校验逻辑拦截，未继续进入后续业务流程；取款金额等于账户可用余额这一临界场景能够正常完成，说明资金扣减逻辑允许合法的边界值，并能正确处理余额归零状态。

在异常输入与安全输入方面，SQL 注入尝试和 XSS 脚本输入均未造成越权登录、脚本执行或页面异常。系统将异常字符作为普通输入处理，登录认证仍按账号密码校验结果返回，页面渲染也未执行脚本内容，说明当前输入处理和展示路径能够覆盖常见恶意输入场景。

交易回调相关测试主要验证幂等边界。BOUND-008 和 BOUND-009 的结果表明，资金回调和持仓回调都能基于业务唯一键识别重复请求。同一 `refOrderId` 及相同业务类型的重复调用不会重复生成资金流水或持仓流水，也不会造成余额、冻结金额、持仓数量的二次改写，能够避免交易系统重试带来的重复记账风险。

账户补办迁移测试覆盖了挂失冻结状态下的资金和证券账户迁移边界。资金账户补办时，旧账户的可用余额与冻结余额能够合并迁移到新账户，并同步完成旧账户清零、销户以及证券账户绑定恢复；证券账户补办时，冻结持仓能够迁移为新账户的可用持仓，旧账户数据被清理，说明补办流程中的状态流转、余额迁移、持仓迁移和绑定关系更新保持一致。

年度结息测试覆盖了零天差和一天差两个关键路径。零天差场景不会重复产生利息或流水，避免了同一日期重复结息；一天差场景能够按照年利率与天数计算利息，并将 `0.0959...` 的计算结果按规则舍入为 `0.10`，最终更新账户余额并记录利息流水。该结果说明利息计算、舍入处理和入账流程符合预期。

综上，BOUND-001 至 BOUND-014 的实际结果全部符合预定结果。本轮边界值与异常测试未发现影响账户开户、资金变更、交易回调、补办迁移和年度结息的异常缺陷，相关业务规则可以支撑后续接口联调和回归测试。

本测试的目的主要是测试本子系统与其他子系统的接口是否完好，能否最后实现集成测试。因为采用的是以数据为中心的体系结构风格，所以与其他子系统的接口测试最终主要集中在与数据库的接口测试上。项目具体信息存放在数据库中，前端通过后端接口从数据库中读取信息，以及从请求中获取登陆状态，实现与其他子系统的交互。

本子系统与其他子系统接口测试将主要测试与数据库的交互能否顺利进行以及用户登录信息能否正确从请求中获取。

- 与交易客户端的接口：
  - 密码修改接口
  - 账户信息快照接口
  - 资金与持仓修改接口
- 与交易管理系统组的接口
  - 创建账户黑名单查询接口

### <a name='-1'></a>5.3. 控制

本子系统根据未登录用户、投资者、普通工作人员和管理员进行访问控制。若用户未登录，则无法进入投资者端或工作人员端的任何业务模块；若已以投资者身份登录并通过证书认证，则只能查看本人的资金账户快照、证券账户和持仓信息，以及修改本人的交易密码或取款密码，不能访问工作人员管理模块；若已以普通工作人员身份登录并通过证书认证，则可以访问仪表盘、证券账户和资金账户管理模块，执行开户、查询、资料修改、挂失、补办、销户、存取款和密码修改等操作；若以管理员 `tradeadmin` 身份登录，则还可以调用管理接口，执行账户冻结、解冻、强制销户和年度结息等操作。

本子系统在证券账户和资金账户开立前，需要从交易管理子系统的黑名单查询接口获取投资者的黑名单状态，黑名单命中时拒绝开户。投资者、证券账户、资金账户、密码哈希、资金流水和操作日志等信息由本子系统统一管理。本子系统向证券交易客户端提供登录认证、资金账户快照和证券持仓快照，并接收交易子系统在委托、成交和撤单后发送的资金及持仓变更信息，以保证不同子系统中的账户数据一致。

## <a name='-1'></a>7. 对软件功能的结论

### <a name='-1'></a>7.1. 证券账户管理功能

#### <a name='-1'></a>7.1.1. 能力

证券账户管理功能已形成较完整的账户生命周期处理能力。系统支持成年自然人及法人开户，能够校验证件格式、投资者年龄、重复开户和黑名单状态；支持账户及持仓快照查询，并依据账户状态限制受限操作；支持持有人资料修改，修改时继续执行证件唯一性和年龄校验；支持挂失、补办和销户，补办时可生成新账号、关闭旧账号并迁移持仓，销户时能够校验持仓是否清零及持有人身份。

边界测试表明，系统能够正确处理持仓冻结量等于全部可卖数量、补办时仅存在冻结持仓等场景。交易联调及压力测试还验证了持仓变更回调的幂等性：同一业务请求重复提交时不会重复修改持仓或重复生成流水。在并发度 24、总任务数 120 的重复持仓回调场景中，120 次请求全部成功，平均耗时为 41.22 ms。

#### <a name='-1'></a>7.1.2. 限制

证券账户功能目前仍受以下因素限制：外部持仓变更接口缺少可靠的系统身份认证或请求签名，不能防止未经授权的调用；账户列表会返回完整身份证号等敏感信息，缺少脱敏和更细粒度的查询权限控制。

此外，证券账户列表、持仓及仪表盘等查询共享当前 DAO 连接方式。在高并发混合查询下，逐条补查和即时创建数据库连接会放大数据库访问次数，因此本功能尚不能证明满足大型的、高并发生产环境的稳定性要求。

### <a name='-1'></a>7.2. 资金账户管理功能

#### <a name='-1'></a>7.2.1. 能力

资金账户管理功能能够完成开户及证券账户绑定、账户登录、密码修改、存款、取款、快照查询、挂失、补办、销户和活期利息处理。系统能够阻止遗漏绑定和重复绑定，按账户状态限制登录及业务操作，并对原密码、两次新密码、交易金额和可用余额进行校验。补办时能够将旧账户可用余额和冻结余额合并迁移至新账户，销户前能够检查余额是否清零；日常计息结果、年度结息结果及相应资金流水均可查询。

边界测试验证了零金额存款、全额取款、补办余额迁移、年度结息零天差和一天差舍入等场景。接口联调验证了交易客户端登录、密码修改、资金冻结、撤单解冻和成交扣款等跨子系统流程，账户数据能够同步更新。资金回调具备幂等处理能力；在并发度 24、总任务数 120 的重复资金回调场景中，120 次请求全部成功，平均耗时为 36.85 ms。

#### <a name='-1'></a>7.2.2. 限制

资金账户的外部余额变更接口当前无需 token 或签名即可调用，攻击者可能伪造交易回调并修改余额，属于上线前必须处理的风险。部分客户端接口通过 URL query 传递 `auth_token`，令牌可能被浏览器历史、代理或服务器日志记录。

性能方面，混合查询场景在并发度 40、总请求数 400 时成功 385 次、失败 15 次，平均耗时 1020.33 ms，P95 为 3495 ms。主要限制是 DAO 层未使用连接池，且仪表盘和账户列表存在逐条补查，短时间大量建连会导致数据库连接及客户端临时端口资源耗尽。因此，资金账户的串行业务流程和回调幂等性已得到验证，但高并发查询能力尚未达到本轮测试的通过标准。

## <a name='-1'></a>8. 分析摘要

### <a name='-1'></a>8.1. 能力

综合模块功能、边界异常、压力、接口联调和安全性测试，账户业务子系统已具备以下能力：

- 工作人员能够登录系统、查看仪表盘和操作日志，停用账号后原有 token 可立即失效。
- 证券账户和资金账户的开户、查询、资料维护、挂失、补办、销户等主要生命周期流程可以正常执行，关键状态流转和前置业务规则有效。
- 资金账户支持登录、密码修改、存取款、余额与冻结资金管理、活期利息和年度结息；证券账户支持持仓查询、持仓冻结与迁移。
- 系统能够处理空值、非法证件、非法金额、余额不足、重复开户、重复绑定、冻结账户及临界金额等异常或边界输入。
- 交易客户端与账户业务子系统之间的密码修改、账户快照、资金冻结、撤单解冻、成交扣款和持仓变更流程可以联调，资金及持仓回调具备幂等性。
- 已验证参数化数据库访问可抵御本轮 SQL 注入载荷，JSON 响应不会直接执行 XSS 脚本；横向越权、伪造 token、停用员工继续访问及错误密码敏感数据回显等场景能够被拦截。
- 自动化安全测试共执行 17 项并全部通过；全量后端测试共 67 项通过、0 项失败，另有 8 项真实 MySQL 集成测试因环境条件跳过。压力测试的 4 个场景中，并发开户和两类重复回调场景通过，混合并发查询场景未通过。

### <a name='-1'></a>8.2. 缺陷和限制

| 优先级 | 缺陷或限制 | 影响 | 建议 |
| ------ | ---------- | ---- | ---- |
| P0 | 外部资金、持仓交易回调缺少认证或签名 | 未授权请求可能直接修改余额或持仓 | 增加 HMAC 签名、时间戳与重放保护，或使用独立的系统 token |
| P0 | 账户列表批量返回完整身份证号 | 可能造成投资者个人敏感信息批量泄露 | 默认脱敏，增加分页、最小字段返回和细粒度权限控制 |
| P1 | 混合并发查询未通过 | 40 并发下出现 15 次连接失败，查询延迟较高 | 引入数据库连接池，消除逐条补查并优化聚合查询 |
| P1 | `auth_token` 通过 URL query 传递 | 令牌可能泄露到历史记录和日志 | 改用 `Authorization: Bearer` 或受保护的请求 Header |
| P1 | 密码使用无 salt 的 SHA-256 | 抗彩虹表和离线破解能力不足 | 改用 BCrypt、PBKDF2 或 Argon2，并使用独立 salt |
| P1 | 数据库配置存在默认凭证且关闭 SSL | 部署配置泄露后可能导致数据库被直接访问或链路被窃听 | 使用环境变量或密钥管理服务，并启用安全连接 |
| P2 | 登录缺少失败限速，CORS 策略不明确 | 增加暴力破解及跨域配置不当风险 | 增加失败计数、冷却或验证码，并显式配置来源白名单 |

综上，系统主要业务流程和数据一致的功能已实现并可用，已可以在一般条件下使用。但如果要在大型生产环境中上线，仍有进一步完善空间。
